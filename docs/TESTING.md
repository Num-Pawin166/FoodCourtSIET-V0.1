## เทสต์แต่ละประเภททดสอบอะไร

### 1. Unit test — ทดสอบฟังก์ชันเดี่ยวๆ
- **Backend** `backend/test/unit.test.js`
  - QR พร้อมเพย์: ตรวจโครงสร้าง EMVCo และ CRC16 โดยเทียบกับอัลกอริทึมที่เขียนแยกอีกแบบ
  - ช่วงเวลารับอาหาร เวลาไทย และการเปลี่ยนสถานะออเดอร์ที่อนุญาต
- **แอปนักศึกษา** `mobile/test/unit/`
  - แปลง JSON เป็น models และป้ายสถานะการชำระเงิน
  - ตะกร้า สั่งอีกครั้ง โหมดออฟไลน์ และเมนูโปรด
  - **ฐานข้อมูล SQLite ในเครื่อง:** ใช้ SQLite จริงผ่าน FFI ตรวจ CHECK constraint, transaction rollback และว่าข้อมูลยังอยู่หลังปิดแล้วเปิดฐานข้อมูลใหม่
  - **รีวิวบน Firestore** (`reviews_test.dart`): ใช้ Firestore จำลอง (`fake_cloud_firestore`) ตรวจว่าบันทึกฟิลด์ครบ, ส่งซ้ำ = แก้รีวิวเดิม, กรองตามร้านและเรียงใหม่สุดก่อน, อัปเดต real-time, ปฏิเสธคะแนนนอกช่วง/ออเดอร์ที่ยังไม่รับ/ข้อความยาวเกิน และย่อชื่อเพื่อความเป็นส่วนตัว
- **แอปร้านค้า** `vendor/test/unit/`
  - **เสียงเตือน:** ใช้นาฬิกาจำลองตรวจว่าดังซ้ำทุก 3 วินาทีและหยุดเมื่อไม่มีออเดอร์รอ
  - models และ AppState
  - **รีวิวร้าน** (`reviews_test.dart`): อ่านเฉพาะรีวิวของร้านตัวเอง เรียงใหม่สุดก่อน, อัปเดต real-time, คำนวณคะแนนเฉลี่ยและจำนวนรีวิวแยกตามดาว, Firebase ใช้ไม่ได้แล้วแจ้งสาเหตุ

### 2. Widget test — ทดสอบหน้าจอทีละหน้า
`mobile/test/widget/` และ `vendor/test/widget/` เรนเดอร์หน้าจอจริงบนขนาดจอมือถือ แล้วต่อกับเซิร์ฟเวอร์จำลอง (`test/support/fake_backend.dart`) จากนั้นกด พิมพ์ และเลื่อนเหมือนผู้ใช้
- **แอปนักศึกษา:** Login, Home (ค้นหา/กรอง), เมนูร้าน, ตะกร้า, ชำระเงิน (จำลองการเลือกรูปสลิป), คำสั่งซื้อ (ไทม์ไลน์/ยกเลิก/ออฟไลน์), AI chat, โปรไฟล์, แถบเมนูล่าง และรีวิวร้าน (ให้ดาว/แก้รีวิว/คะแนนเฉลี่ย/รีวิวใหม่ขึ้นทันที/Firebase ล่มแล้วหน้าร้านยังใช้ได้)
- **แอปร้านค้า:** ออเดอร์ (เสียงเตือน/รับ/ปฏิเสธ/ตรวจสลิป), เมนู (เพิ่มพร้อมรูป/แก้/ลบ), ร้านของฉัน (เวลา/พร้อมเพย์/รูปร้าน/เปลี่ยนรหัสผ่าน), แท็บรีวิว (คะแนนเฉลี่ย/แถบสัดส่วนดาว/ไม่เห็นรีวิวร้านอื่น/รีวิวใหม่ขึ้นทันที/Firebase ล่มแล้วแจ้งสาเหตุ)

### 3. Integration test — ทดสอบหลายส่วนทำงานร่วมกัน
- **Backend** `backend/test/integration.test.js` และ `google.test.js`
  - เปิด API จริงบนพอร์ตสุ่มกับฐานข้อมูล SQLite ชั่วคราว แล้วยิง HTTP จริงตั้งแต่สั่งอาหารจนรับอาหาร
  - การจ่ายเงิน: แนบสลิป → ร้านปฏิเสธ → แนบใหม่ → ร้านยืนยัน
  - เมนูและรูป, แอดมิน, AI (ทั้งแบบใช้กฎและแบบ Gemini ที่จำลองคำตอบ) และล็อกอิน Google
- **แอปนักศึกษา** `mobile/test/integration/app_flow_test.dart`
  - เปิดทั้งแอปจาก `main.dart` แล้วไล่ตั้งแต่ล็อกอิน → เลือกร้าน → ใส่ตะกร้า → สั่ง → จ่ายพร้อมเพย์ → แนบสลิป → ดูคิว
  - AppState ทำงานร่วมกับ SQLite จริง: ปิดแล้วเปิดแอปใหม่ตะกร้ายังอยู่, เน็ตหลุดยังเห็นเลขคิว
  - รีวิวจากแท็บประวัติ แล้วเปิดแอปเป็นผู้ใช้อีกคนที่ใช้ Firestore ชุดเดียวกัน → เห็นรีวิวนั้นในหน้าร้าน
- **แอปร้านค้า** `vendor/test/integration/vendor_flow_test.dart`
  - ออเดอร์เข้า → เสียงดังซ้ำและแถบแดงขึ้นทุกแท็บ → รับ → ตรวจสลิป → ทำ → พร้อม → ลูกค้ารับ

### 4. Security test — ทดสอบความปลอดภัย
- **Backend** `backend/test/security.test.js` และ `google.test.js`

  | ตรวจอะไร | ผลที่ถูกต้อง |
  |---|---|
  | ไม่มี token / token ปลอม / หมดอายุ / บัญชีถูกลบ | ได้ 401 |
  | ปลอม role ใน token เป็น admin | ได้ 403 (ระบบเชื่อ role จากฐานข้อมูล) |
  | นักศึกษาเรียก API ร้านหรือแอดมิน | ได้ 403 |
  | ร้าน B เข้าถึงออเดอร์ สลิป หรือเมนูของร้าน A / นักศึกษาคนอื่นดูออเดอร์ของเรา | ได้ 404 |
  | เปิดสลิปผ่าน URL รูปสาธารณะ | เปิดไม่ได้ |
  | API สาธารณะ | ไม่เผยหมายเลขพร้อมเพย์จริง |
  | ส่งราคาหรือยอดรวมปลอมจากแอป | ระบบไม่สนใจ คิดราคาจากฐานข้อมูล |
  | จำนวนติดลบหรือทศนิยม | ถูกปฏิเสธ |
  | SQL injection | ไม่มีผล |
  | ไฟล์ปลอมที่ตั้งชื่อเป็น .png หรือไฟล์ใหญ่เกิน 2 MB | ถูกปฏิเสธ |
  | error ภายในระบบ | ไม่หลุดรายละเอียดออกไป |
  | ถาม AI เกิน 10 ครั้งต่อนาที | ได้ 429 |
  | Google: gmail, โดเมนหลอก, อีเมลยังไม่ยืนยัน, ชื่อผู้ใช้ชนกับบัญชีร้านหรือแอดมิน | ถูกปฏิเสธทั้งหมด |
- **Firestore security rules** `firestore/test/rules.test.js`
  - รันบน **Firestore Emulator ของ Google จริง** (ไม่ใช่ตัวจำลอง) จึงตรวจ rules ได้ตรงกับที่ใช้บน cloud

  | ตรวจอะไร | ผลที่ถูกต้อง |
  |---|---|
  | ไม่ได้ล็อกอิน อ่านหรือเขียน | ถูกปฏิเสธ |
  | สร้างรีวิวโดยใส่ `authorUid` เป็นคนอื่น / แก้รีวิวของคนอื่น / เขียนทับทั้ง doc | ถูกปฏิเสธ |
  | doc id ไม่ตรงกับเลขออเดอร์ | ถูกปฏิเสธ |
  | คะแนน 0, 6, -1, 4.5, "5" | ถูกปฏิเสธ (ต้องเป็นจำนวนเต็ม 1–5) |
  | ความคิดเห็น 301 ตัว / ชื่อว่าง / ชื่อยาวเกิน 60 | ถูกปฏิเสธ (300 ตัวพอดีผ่าน) |
  | แนบฟิลด์แปลกปลอม เช่น `verified: true` | ถูกปฏิเสธ |
  | ปลอมเวลาแทนเวลาเซิร์ฟเวอร์ | ถูกปฏิเสธ |
  | เจ้าของย้ายรีวิวไปร้านอื่น / เปลี่ยนเจ้าของ / ลบรีวิว | ถูกปฏิเสธ |
  | collection อื่น | อ่าน/เขียนไม่ได้ทั้งหมด |
- **แอปทั้งสอง** `test/security/`
  - ส่ง token เฉพาะหลังล็อกอิน และเจอ 401 แล้วออกจากระบบอัตโนมัติ
  - บัญชีผิดบทบาทเข้าแอปไม่ได้
  - ออกจากระบบแล้วล้าง token, ตะกร้า, ออเดอร์ที่แคชไว้ และแชต AI ในเครื่อง (กันคนถัดไปที่ใช้มือถือเครื่องเดียวกันเห็น)
  - ช่องรหัสผ่านซ่อนตัวอักษร

## วิธีรันเอง

```bash
# Backend
cd backend
npm test                 # รันทุกเทสต์
npm run test:coverage    # + รายงาน coverage (ไม่ผ่านถ้า < 70%)

# แอปนักศึกษา / แอปร้านค้า
cd mobile      # หรือ cd vendor
flutter test                         # รันทุกเทสต์
flutter test test/security           # เฉพาะประเภท: unit | widget | integration | security
flutter test --coverage
python ../scripts/check_coverage.py coverage/lcov.info 70

# Firestore security rules (ต้องมี Java 11+ — เปิด Emulator ให้เองแล้วปิดเมื่อจบ)
cd firestore
npm install
npm test
```

## GitHub Actions CI

ไฟล์ `.github/workflows/ci.yml` จะรันทุกครั้งที่ push ขึ้น `main` หรือเปิด Pull Request

| Job | ขั้นตอน |
|---|---|
| **Backend** | `npm ci` → เทสต์ทั้งหมดพร้อมวัด coverage (≥ 70%) → เปิดเซิร์ฟเวอร์จริงแล้วเช็ก `/api/health` |
| **Firestore rules** | `npm ci` → เปิด Firestore Emulator → รันเทสต์ security rules |
| **Student app** | `flutter analyze` → `flutter test --coverage` → เช็ก coverage ≥ 70% → **build APK (release)** |
| **Vendor app** | เหมือน Student app |

ผลลัพธ์ที่ได้:
- **ดาวน์โหลด APK** ที่ build เสร็จได้จากหน้า Actions ของแต่ละรอบ (Artifacts)
- **ไฟล์ coverage (lcov.info)** ของทุกส่วน
- **badge สถานะ** ใส่ใน README ได้ด้วยโค้ดนี้:
  ```markdown
  ![CI](https://github.com/<owner>/<repo>/actions/workflows/ci.yml/badge.svg)
  ```
